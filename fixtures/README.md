# Fixtures

Every file here is synthetic: `com.example.app`, tokens `tok_` plus a few characters, users `u_1` to `u_9`, order id `GPA.0000-0000-0000-00000`. They are the test suite, and the best way to learn the timeline format.

| Folder | What it holds |
|---|---|
| `rules/` | One minimal timeline per rule, named `<id>-<slug>.json`, with `<id>-<slug>.expected.json` beside it: the smallest timeline that triggers exactly that rule and nothing else. `node --test tests/rules-B.test.js` runs group B. |
| `clean/` | Five correct lifecycles that must produce zero findings, forever: purchase to renewal to cancellation to expiry; an upgrade with the old token invalidated; grace period then recovery; pause then resume; a prepaid plan with a top-up. A false positive here is a release blocker. |
| `composite/` | Three realistic weeks that produce several findings; the order and the evidence indexes are the test. |
| `rtdn/` | Pub/Sub push envelopes, one per notification kind, for `billing-doctor rtdn`. |
| `subscriptions/` | `purchases.subscriptionsv2` resources, one per state worth explaining, for `billing-doctor state`. |
| `example-timeline.json` | The example from the format documentation. |

Try one:

```bash
billing-doctor diagnose fixtures/rules/G2-void-then-active.json
billing-doctor diagnose fixtures/composite/01-week-upgrade-refund-duplicate.json
billing-doctor diagnose fixtures/clean/03-grace-then-recovery.json
```

The rule and clean fixtures are generated by `scripts/fixtures.mjs` (with `fixtures-DG.mjs`, `fixtures-AHIJ.mjs` and `fixtures-composite.mjs`), so every fixture shares the same correct preamble: a purchase, a verification, a grant with an idempotency key, an acknowledgement, the notification, a re-fetch, and the write. Each fixture then adds the one thing that goes wrong. Edit the script, run `node scripts/fixtures.mjs`, and check the diff.
